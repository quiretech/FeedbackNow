1. PROJECT OVERVIEW (ONE-LINER / BULLET CONTEXT)
--------------------------------------------------------------------------------
• LoRaWAN IoT edge device (nRF52840 + Zephyr RTOS): uplink/downlink with AWS IoT Core and ChirpStack; 4.2" E-paper display (SSD1683), NFC (PN5180), SD card logging; multi-rail power management and shared-SPI arbitration.
• Full stack: embedded firmware (Zephyr on nRF52840), LoRaWAN (SX1262), cloud (AWS Lambda, IoT Rules), optional RPi/ChirpStack gateway.

--------------------------------------------------------------------------------
2. RTOS CONCEPTS (ZEPHYR / KERNEL)
--------------------------------------------------------------------------------
• Multithreading: Dedicated threads for state manager, LoRa manager, button, LED, NFC, system monitor, SD logger worker; priorities and stack sizes defined in sys_config.h (e.g. STATE_MANAGER 1, LORA 2, LED 3, BUTTON 4).
• Synchronization: k_mutex (state, LoRa status, NFC, SPI bus, power rail, SD, metrics), k_sem (state change notification), k_condvar (power rail manager: wait for ON/OFF holds to clear).
• Message queues: k_msgq for button events, LED commands, LoRa messages, state events, NFC events, downlink payloads (main ↔ LoRa), SD downlink log items; fixed-size, NUL-terminated handling for downlink to avoid buffer overread.
• Deferred work: k_work + k_work_queue for LED blink-off, LoRa retry, heartbeat, SD writes (dedicated workqueue so SD can block on 3V3A without starving system workqueue).
• Timers: k_timer for LVGL tick fallback, downlink restore delay, LED blink, heartbeat, LoRa retry.
• Kernel config: CONFIG_MULTITHREADING, CONFIG_THREAD_STACK_INFO, CONFIG_INIT_STACKS, CONFIG_STACK_CANARIES, CONFIG_TICKLESS_KERNEL; CONFIG_MPU, CONFIG_ARM_MPU, CONFIG_MPU_STACK_GUARD for memory protection.

--------------------------------------------------------------------------------
3. MULTIPLE DRIVER DEVELOPMENT (CUSTOM + DEVICE TREE)
--------------------------------------------------------------------------------
• Custom Zephyr drivers with DTS bindings:
  - PN5180 (NXP NFC reader): nxp,pn5180 — SPI + irq/rst/busy/nss GPIOs, timeout-ms; config/data structs, busy/available polling, mutex-protected API.
  - SSD1683 (Solomon E-paper): solomon,ssd1683 — width/height, dc/reset/busy GPIOs, optional fast-mode; Zephyr display API, LVGL integration; low-level command/data writes, busy wait, partial/full refresh.
• Zephyr subsystem usage: SPI (spi_dt_spec, spi_write_dt/read_dt), GPIO (gpio_dt_spec), EEPROM (zsk/lora devnonce persistence), disk_access + FAT (SD), LoRaWAN (lorawan_send, downlink callback).
• Shared SPI bus: Single Arduino SPI with multiple CS (LoRa, EPD, SD, PN5180); spi_mutex for thread-safe access; EPD flush and SD access serialize via mutex + power rail hold.
• Board/overlay: nrf52840dk overlay for buttons, LEDs, power enables (3V3, 1V8, 3V3A, 3V6), UART, SX1262, SSD1683, SDHC SPI slot, PN5180; chosen zephyr,display = &ssd1683.

--------------------------------------------------------------------------------
4. SYSTEM ARCHITECTURE & CONCURRENCY
--------------------------------------------------------------------------------
• State machine: state_manager — explicit states (INIT, READY, PROCESSING, SENDING, ERROR, SLEEP); events (button, LoRa sent/failed, LED, NFC, system ready); state transition table; event queue consumed by state manager thread; state_change_sem for “wait for state.”
• Power rail arbitration: power_rail_mgr — reference-counted ON/OFF holds for 3V3A (LoRa needs OFF during RX/TX; EPD/NFC/SD need ON) and 3V6 (NFC); k_mutex + k_condvar; OFF wins for 3V3A; clients (LORA, NFC, EPD, BOOT, SD); stabilization delays after rail changes.
• Power sequencing: power_ctrl (GPIO enables for 3V3, 1V8, 3V3A, 3V6); init order: power rails → power_rail_mgr → SD logger (lazy mount) → system_init (spi_mutex, buttons, LEDs, lora_app) → state/lora/led/monitor/heartbeat → display init with 3V3A hold → thread starts.
• LoRa + display coexistence: LoRa thread holds 3V3A OFF for send + guard; main thread requests 3V3A ON only when EPD flush pending; SPI mutex ensures EPD and SD don’t use bus concurrently.

--------------------------------------------------------------------------------
5. FIRMWARE / PERIPHERAL HIGHLIGHTS
--------------------------------------------------------------------------------
• LoRaWAN: Class A (US915); join with stored keys; confirmed/unconfirmed; downlink callback; devnonce in EEPROM (zsk devnonce_store: dual-slot, CRC, monotonic increment) to satisfy network server; NVS/key handling in zsk.
• Storage: FAT on SPI SD (disk_access, SDHC slot); lazy mount per write to avoid power-cycled card; downlink log via workqueue; EEPROM for devnonce (and optional key storage in zsk).
• Display: LVGL on SSD1683; custom fonts (Roboto, Noto Kufi Arabic); downlink shown fullscreen then restore after timer; EPD only powered (3V3A) during flush to preserve panel and save power.
• NFC: PN5180 for tag read; dedicated thread; trigger from button; event queue to state manager.
• Buttons/GPIO: gpio-keys (multiple buttons); button thread forwards to state manager and LED blink; Button 5 triggers NFC scan.

--------------------------------------------------------------------------------
6. CLOUD / BACKEND (FOR FULL-STACK BULLETS)
--------------------------------------------------------------------------------
• AWS: IoT Core LoRaWAN; uplink → IoT Rule → Lambda (uplink_lambda.py); Lambda parses button payloads, converts timestamp to EST, builds downlink payload, invokes send-downlink Lambda (double Base64); optional continuous downlink path.
• ChirpStack: zsk/lora has scripts (chirpstack_onboard, grpc), EUI registry; compatible with RPi + SX12 gateway.
• Payload encoding: Hex-encoded downlink in firmware; Lambda side channel/type/template/module/size/content/control fields.

8. BULLET-READY PHRASES (COPY-PASTE / ADAPT)
--------------------------------------------------------------------------------
• Designed and implemented multi-threaded Zephyr RTOS firmware on nRF52840 with prioritized threads, message queues, mutexes, and condition variables for state machine, LoRa, NFC, and display subsystems.
• Developed custom Zephyr drivers and device tree bindings for NXP PN5180 (NFC) and Solomon SSD1683 (E-paper); integrated with LVGL and shared SPI bus under mutex.
• Architected power rail arbitration (reference-counted ON/OFF holds with condvar) so LoRa radio (3V3A OFF during RX/TX) coexists with EPD, NFC, and SD on shared power and SPI.
• Implemented LoRaWAN Class A (SX1262) with EEPROM-persisted devnonce and dual-slot CRC records to satisfy network server join semantics; uplink/downlink and AWS Lambda integration.
• Added FAT filesystem logging on SPI SD with lazy mount and dedicated workqueue to avoid blocking system workqueue while holding 3V3A for SD access.
• Built event-driven state machine (init/ready/processing/sending/error) with cross-thread events (button, LoRa, LED, NFC) and state transition table.
• Enabled MPU, stack canaries, and tickless kernel; tuned stack sizes and thread priorities for stability on resource-constrained MCU.

• Captured hardware BOM and interfaces: NRF52840, 6 buttons (0–5), PN5180 (ISO15693), SX1262, optional E-paper, RTC, SDHC, EEPROM, 1 LED, battery ADC; two firmware variants (with/without EPD) from single codebase (CONFIG_EPD_ENABLED).
• Defined user roles and flows: Public (single-button feedback vote, 5s lockout) vs Staff (Button 0+1 hold 2s → Staff Mode; button-then-NFC for check-in/check-out/registered vote); button layout (Green=check-in, Yellow=check-out, Red=issue votes); 4-byte User ID from NFC block for backend session logic.
• Specified state machine and timeouts: Normal, Staff Mode (10s), NFC Scan (5s), Device Info (0+1+5 hold 3s, 30s), Reboot (all 6 hold 10s); LED patterns for power-on, join success, button accepted, NFC wait/success/fail, check-in/check-out/vote confirm, reboot; EPD states (Last Cleaned, Thanks, Cleaning in progress, Device Info, Connecting).
• Documented LoRa: uplink event types (0x00–0x06: button, check-in, check-out, registered vote, heartbeat, low battery, storage warning); downlink commands (EPD update, refresh, status request, reset counters); OTAA, Class A, US915/EU868; daily heartbeat with DevEUI jitter; RTC sync via DeviceTimeReq.
• Specified offline resilience: EEPROM queue (50 events), FIFO overflow, flush on reconnect with rate limiting; rejoin every 1 hour when disconnected; device never shuts down on network failure; boot sequence (power-on → HW init → EEPROM → SDHC → RTC → EPD → LoRa init → join → RTC sync → boot uplink → Normal); housekeeping (RTC resync, battery sample, EEPROM→SDHC flush, counter validation, SDHC health, EPD refresh).
• Error-handling table: join failure, uplink failure, NFC read fail/timeout, SDHC mount/full, EEPROM CRC, RTC invalid, low battery; network recovery diagram (graceful reconnection, queue flush); design principle: unattended deployment, no permanent shutdown on network loss.
